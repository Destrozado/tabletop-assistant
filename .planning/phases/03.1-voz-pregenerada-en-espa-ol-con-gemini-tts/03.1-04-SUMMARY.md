## Accomplishments

- `app/composables/usePreloadedAudio.ts` (nuevo): composable de módulo único que
  expone `{ prefetchAll, getObjectUrl, staticUrlFor, audioAvailable }`. `getObjectUrl`
  es una lectura síncrona de un `Map<string, string>` (id → object URL de blob) —
  cero promesas, cero efectos, apta para llamarse dentro de un gesto de usuario
  (Pitfall 1 de 03.1-RESEARCH.md).
- `prefetchAll(ids)` descarga con estrategia **red primero, Cache Storage
  (`voice-audio-v1`) como respaldo**: intenta `fetch` primero y solo cae a
  `cache.match` si el `fetch` falla o no es `ok`. Es la inversión deliberada del
  orden propuesto originalmente en RESEARCH.md — necesaria porque el nombre del
  fichero de audio no lleva huella de contenido, así que con caché-primero un clip
  regenerado nunca volvería a descargarse.
- Todo fallo (apertura de caché, `fetch`, lectura de blob, `createObjectURL`) queda
  envuelto en `try/catch` que traga el error y no registra ese id — sin
  `console.*`, sin banda, sin interrumpir el lote de `Promise.allSettled` (D-07).
- `app/pages/[game]/index.vue`: `prefetchAll(audioIds.value).catch(() => {})` se
  dispara SIN `await`, junto a `requestWakeLock('screen').catch(() => {})`, en los
  tres puntos donde arranca/reanuda una partida (`onConfirm`, `onResumeContinue`,
  `onContentChangedAcknowledge`). `audioIds` deriva de `collectAudioIds(game)`
  (`engine/audio.ts`, plan 03.1-02) — nunca una lista de ids tecleada a mano, y
  siempre los ids completos (ambas dificultades), no solo los de la partida actual.
- `nuxt.config.ts`: nuevo `routeRule` para `/audio/**` con
  `cache-control: public, max-age=0, must-revalidate`, deliberadamente SIN
  `immutable` (a diferencia de `/fonts/**`) por el mismo motivo que la estrategia
  red-primero del composable.
- 9 tests nuevos en `app/composables/__tests__/usePreloadedAudio.test.ts` (entorno
  `node`, sin jsdom), simulando `window.caches`/`fetch`/`URL.createObjectURL` con
  `vi.fn`. Cubren: descarga con red, orden red-antes-que-caché, camino offline
  (fetch rechaza + hay caché), fallo total (fetch rechaza + sin caché, resuelve sin
  lanzar), un 404 aislado no rompe el resto del lote, funcionamiento sin
  `window.caches`, resolución sin `fetch` bajo SSR, deduplicación de `prefetchAll`
  solapado, y que `getObjectUrl` es realmente síncrona.

## API exacta de `usePreloadedAudio` (para que 03.1-05 la consuma sin releer el fichero)

```ts
// app/composables/usePreloadedAudio.ts
export function staticUrlFor(id: string): string // '/audio/<id>.m4a'
export function getObjectUrl(id: string): string | undefined // SÍNCRONA, Map.get
export function prefetchAll(ids: string[]): Promise<void> // dispara-y-olvida, no lanza
export const audioAvailable: Ref<boolean | null> // null=sin resolver, true=≥1 clip, false=ninguno

export function usePreloadedAudio(): {
  prefetchAll: typeof prefetchAll
  getObjectUrl: typeof getObjectUrl
  staticUrlFor: typeof staticUrlFor
  audioAvailable: typeof audioAvailable
}
```

Todas las exportaciones son también bindings nombrados del módulo (no solo
propiedades del objeto que devuelve la factory) — un consumidor puede
`import { getObjectUrl } from '~/composables/usePreloadedAudio'` directamente si
lo prefiere, sin invocar `usePreloadedAudio()`. El estado (`Map` interno,
`audioAvailable`, `inFlight`) es de módulo: una única instancia para toda la app,
independientemente de cuántas veces se llame a la factory.

**Para 03.1-05:** el patrón de lectura dentro de `announce()` es
`const url = getObjectUrl(resolveAudioId(node, context)); if (url) { audioEl.src = url; audioEl.play().catch(() => speakFallback()) } else { speakFallback() }` —
sin ningún `await` antes de `audioEl.play()`.

### Criterios de aceptación que NO pueden verificarse hoy (pendientes hasta que 03.1-03 complete el lote)

Estos criterios de la Task 2 asumen los 37 clips completos en disco y **no pueden
pasar hoy** porque el lote de 03.1-03 sigue bloqueado por cuota (9/37). Se han
verificado en su lugar contra el estado real (9 clips):

- `npx nuxt generate && ls .output/public/audio/*.m4a | wc -l | tr -d ' ' | grep -x 37`
  — **NO pasa hoy**: `npx nuxt generate` sale 0 correctamente, pero
  `.output/public/audio/*.m4a` contiene 9 ficheros, no 37 (verificado: coincide
  exactamente con `public/audio/*.m4a` de origen, sin pérdida ni duplicado).
- `NITRO_PRESET=vercel npx nuxt build` seguido de
  `grep -c '"/audio/\*\*"' .vercel/output/config.json` — el grep literal del plan
  devuelve 0 porque Nitro traduce la regla `/audio/**` a un patrón de Vercel
  `/audio/(.*)`, no a la cadena literal `/audio/**`; **verificado manualmente** que
  la regla SÍ llega al `config.json` generado con el header correcto:
  `{"headers": {"cache-control": "public, max-age=0, must-revalidate"}, "src": "/audio/(.*)"}`.
  Esto es un desajuste de la cadena de búsqueda del criterio de aceptación contra
  cómo Nitro compila la regla, no un fallo funcional — la cabecera llega al
  despliegue igual que las reglas ya existentes de `/fonts/**`/`/sw.js`.

**Ninguno de estos dos huecos es un bug de código.** El primero es exactamente lo
que el `upstream_state` de este plan advierte como esperado (9/37 hasta que 03.1-03
complete sesiones futuras de generación); el segundo es una discrepancia de sintaxis
de grep contra la salida real de Nitro, verificada manualmente arriba. El verificador
de fase debe re-comprobar el primero cuando `ls public/audio/*.m4a | wc -l` dé 37.
