## Summary

Esta fase añade una segunda fuente de locución (audio grabado) delante de la síntesis
de voz ya construida en la Fase 3, sin tocar esa capa. Todo lo verificado empíricamente
en `03.1-FINDINGS.md` (endpoint, modelo, formato PCM crudo, `afconvert` sin ffmpeg,
compresión ~5:1) se da por bueno; esta investigación se centra en los cinco huecos que
CONTEXT.md deja a discreción: formato final del audio, el riesgo real del gesto de
usuario en iOS Safari aplicado a `<audio>.play()`, la estrategia de precarga sin service
worker, el identificador estable de las 4 variantes de dificultad, y la forma exacta del
script/gate de deriva.

El hallazgo más importante no estaba en la lista de preguntas: **el proyecto ya resuelve
el riesgo del gesto de iOS por construcción**. Cada punto donde hoy se llama a
`announce()` (`onNext`, `onBack`, `onIndexJumpTo`, `onResumeContinue`) es ya, por diseño
de la Fase 3 (D-42), una llamada síncrona dentro del manejador de toque del botón. Si el
camino de audio grabado llama a `audioEl.play()` en el mismo punto síncrono (nunca tras
un `await` de red), no hace falta ningún truco de "desbloqueo" de `<audio>`/Web Audio
propio de apps de juegos: la disciplina que iOS exige para `<audio>.play()` es la misma
que ya exige para `speechSynthesis.speak()`, y el código ya la respeta en los cuatro
sitios que importan. El riesgo real no es "cómo desbloquear audio en iOS", es "no
introducir un `await` entre el toque y el `.play()`" — y eso es una revisión de código,
no una API nueva que aprender.

El segundo hallazgo relevante: **esta fase no añade ninguna dependencia npm nueva**. La
reproducción usa `HTMLAudioElement`/`fetch`/`Cache Storage`, todas nativas del navegador;
el script de generación usa `fetch`, `node:child_process` (para invocar `afconvert`),
`node:crypto` (hash) y `node:fs`, todas nativas de Node 22 (instalado: v22.17.1). El
único punto de fricción de plataforma es que `--env-file` de Node solo pasó a estable en
v22.21.0 — con v22.17.1 sigue funcionando pero emite un `ExperimentalWarning` en stderr;
irrelevante para un script de un solo desarrollador, pero documentado para que no
sorprenda.

**Primary recommendation:** Formato final `.m4a` (AAC-LC 64kbps vía `afconvert`, tal como
ya midió `03.1-FINDINGS.md`); identificador de variante `${step.id}.${difficulty}` para
los 4 casos con `variants.difficulty` (mismo campo que ya usa `resolveText()` para
decidir qué texto mostrar); precarga vía `fetch()` → `Blob` → `URL.createObjectURL()` en
un mapa en memoria, respaldado oportunísticamente por la Cache API (sin service worker)
para sobrevivir a un recargo de página a mitad de partida; manifiesto de huellas fuera de
`public/` (en `scripts/voice/manifest.json`, nunca servido al cliente); reproducción
cableada exactamente en los mismos cuatro sitios síncronos donde hoy vive `announce()`.

### Pattern 1: Identificador estable de las 4 variantes de dificultad

**What:** `content/marvel-champions.json` declara `variants.difficulty` en exactamente 2
pasos ([VERIFIED: recuento programático sobre el fichero real, ver §Sources] —
`setup.encuentros.03` y `setup.escenario.04`), cada uno con `normal` y `expert`, 4 frases
`speech` en total sin `id` propio.

**When to use:** Para nombrar el fichero de audio y la clave del manifiesto de huellas de
esas 4 frases.

**Recomendación:** `${step.id}.${difficulty}` — p. ej. `setup.encuentros.03.normal.m4a`,
`setup.encuentros.03.expert.m4a`. Es exactamente el mismo dato (`step.id` +
`context.difficulty`) que ya usa `engine/resolve.ts` para decidir qué `speech` mostrar:

```typescript
// Source: engine/resolve.ts (código real de este repo, líneas 8-9)
const variant = node.step.variants?.difficulty?.[context.difficulty]
return { /* ... */ speech: variant?.speech ?? node.step.speech }
```

La función `resolveAudioId` que decide el fichero de audio a reproducir debe ser el
espejo exacto de esa rama:

```typescript
// Nueva función, mismo patrón que resolveText — vive junto a ella o en el
// composable de voz. NO reimplementa la lógica de variante: solo decide el
// identificador, resolveText() ya decidió qué texto/speech se muestra.
export function resolveAudioId(node: RuntimeStepNode, context: SessionContext): string {
  const hasVariant = node.step.variants?.difficulty?.[context.difficulty] !== undefined
  return hasVariant ? `${node.step.id}.${context.difficulty}` : node.step.id
}
```

Es determinista, sin colisión (los 33 ids base ya son únicos por el gate de esquema
existente; añadir el sufijo `.normal`/`.expert` solo a los 2 que lo necesitan no puede
colisionar con ningún id base porque ningún id existente termina en esos dos sufijos —
verificable por grep) y sobrevive a ediciones de contenido futuras sin renombrar nada
manualmente.

### Pattern 2: Reproducción sin romper el gesto de iOS

**What:** Cada disparador de `announce()` hoy (`onNext`, `onBack`, `onIndexJumpTo`,
`onResumeContinue` en `app/pages/[game]/index.vue`) es una llamada síncrona dentro de un
manejador de clic, exactamente la disciplina que CLAUDE.md exige para
`speechSynthesis.speak()` en iOS Safari.

**When to use:** Siempre — es la única disciplina que importa para este pitfall.

**Regla dura para el plan:** la nueva rama de audio grabado dentro de `announce()` no
puede introducir NINGÚN `await` entre la entrada a la función y la llamada a
`audioEl.play()`. Esto significa:
- El `Map<id, objectUrl>` de precarga debe leerse de forma síncrona (ya poblado por el
  prefetch en segundo plano, ver Pattern 3) — nunca `await preloadedMap.get(id)`.
- Si el id no está en el mapa (aún descargando, o la descarga falló), caer al
  `speechSynthesis` existente en el mismo tick, no esperar a que termine de llegar.
- `audioEl.play()` devuelve una Promise; su manejo (`.catch(...)`) es async **después**
  de haberla invocado — eso es seguro, lo que no puede ser async es la decisión de
  llamarla.

```typescript
// Patrón recomendado dentro de useVoiceAnnouncer.ts — reemplaza el cuerpo de
// announce() manteniendo TODA la lógica existente (guardas, watchdog G-01,
// detección es-ES) intacta para el camino de fallback.
function announce(): void {
  const kind = currentNode.value?.step.kind ?? null
  if (!shouldAnnounce({ kind, state: voiceState.value, line: spokenLine.value, isSupported: isSupported.value })) return

  const audioId = currentNode.value ? resolveAudioId(currentNode.value, session.context) : null
  const objectUrl = audioId ? preloadedAudio.get(audioId) : undefined

  if (objectUrl) {
    audioEl.src = objectUrl
    audioEl.currentTime = 0
    audioEl.play().catch(() => {
      // D-07: fallo silencioso — Promise rejection (autoplay bloqueado,
      // formato no soportado, elemento no listo) cae al camino existente.
      speakFallback()
    })
    return
  }
  speakFallback() // el cuerpo actual íntegro de announce(): speak() + watchdog G-01
}
```

**No hace falta ningún "desbloqueo" previo de `<audio>`/AudioContext** (el patrón típico
de juegos web de reproducir un buffer silencioso al primer toque): cada llamada real a
`.play()` YA ocurre dentro de un gesto de usuario fresco, igual que `speak()` hoy. Esto
reduce el riesgo frente a lo que plantea la pregunta de investigación original — el
problema no es "cómo desbloquear", es "no dejar que se cuele un `await` en medio".
[MEDIUM confidence — el patrón general de iOS Safari (gesto síncrono habilita
`play()`/`speak()` indistintamente) está bien documentado y es consistente entre
fuentes, pero no se ha verificado en el modelo de tablet real de este proyecto, que
sigue sin conocerse (bloqueante abierto desde la Fase 1). **De-risking recomendado:**
incluir como primera tarea del plan un spike manual en un dispositivo iOS real (o el más
cercano disponible) que solo verifique que `audioEl.play()` invocado así no lanza
`NotAllowedError`, antes de construir el resto de la integración encima.]

Un único elemento `<audio>` reutilizado (no un pool) es suficiente: igual que la síntesis
de voz de hoy, solo suena una locución a la vez (VOZ-04 — nunca se encolan ni repiten),
así que reasignar `.src` y llamar `.play()` en el mismo elemento reproduce exactamente el
modelo mental ya existente.

### Pattern 3: Precarga sin service worker (D-09)

**What:** Descargar los 37 clips (~600-700 KB) en segundo plano al empezar la partida,
sin bloquear el primer paso, y sin un service worker (llega en la Fase 4).

**Recomendación:** `fetch()` → `Blob` → `URL.createObjectURL()` en un `Map` en memoria,
respaldado por la Cache Storage API (`window.caches`, sin registrar ningún service
worker) para que sobreviva a un recargo de página dentro de la misma partida.

```typescript
// Nuevo composable, p. ej. usePreloadedAudio.ts. Se invoca en onConfirm()/
// onResumeContinue() — el mismo punto donde ya se pide el wake lock (D-51) —
// pero SIN esperar su resultado ahí (fire-and-forget, D-09 no bloquea).
const CACHE_NAME = 'voice-audio-v1'
const preloaded = new Map<string, string>() // id -> object URL

async function prefetchAll(ids: string[]): Promise<void> {
  const cache = 'caches' in window ? await window.caches.open(CACHE_NAME) : null
  await Promise.allSettled(ids.map(async (id) => {
    const url = `/audio/${id}.m4a`
    try {
      let response = cache ? await cache.match(url) : undefined
      if (!response) {
        response = await fetch(url)
        if (cache && response.ok) await cache.put(url, response.clone())
      }
      if (!response.ok) return // D-07: ausencia silenciosa, el fallback ya lo cubre
      const blob = await response.blob()
      preloaded.set(id, URL.createObjectURL(blob))
    }
    catch {
      // Sin red, sin audio para este id: silencioso por diseño (D-07).
    }
  }))
}
```

**Por qué no `<link rel="preload">` ni `new Audio(src).load()` solos:** ambos dependen de
la caché HTTP del navegador, que no da ninguna garantía de "disponible offline" ni una
promesa que el código pueda esperar de forma fiable — no encajan con el requisito D-09 de
saber cuándo los 37 están listos. **Por qué Cache Storage y no solo Blob en memoria:** un
recargo de página (p. ej. tras desbloquear la tablet) borra cualquier `Map` en memoria;
Cache Storage persiste entre recargos dentro de la misma sesión de navegador, así que el
`prefetchAll` de un segundo montaje encuentra los clips ya cacheados y solo necesita
volver a materializar los `object URL` (rápido, sin red). [MEDIUM confidence — el soporte
de Cache Storage desde el contexto `window` (sin service worker) está confirmado por MDN
y por la documentación de Workbox/Chrome, pero Safari ha tenido históricamente
comportamiento inconsistente de persistencia entre reinicios completos de la app en iOS
12; no reverificado contra una versión actual de iPadOS. **De-risking recomendado:**
tratar la persistencia entre recargos como *best-effort* — si `cache.match()` falla o
Cache Storage no está disponible (`'caches' in window` es `false`), el código cae
directamente a `fetch()` normal sin cachear, y el fallback a `speechSynthesis` (D-07)
sigue cubriendo cualquier hueco.]

**Implicación de memoria:** 37 `Blob`s de audio comprimido sumando ~600-700 KB es
irrelevante para cualquier tablet moderna; no hace falta ninguna estrategia de liberación
mientras dura la partida. Los `object URL` deben revocarse (`URL.revokeObjectURL`) solo
al desechar el scope del composable (mismo patrón `tryOnScopeDispose` que ya usa
`useVoiceAnnouncer.ts` para el watchdog G-01 y la detección es-ES), nunca durante la
partida.

### Anti-Patterns to Avoid

- **Desbloquear `<audio>` con un buffer silencioso al primer toque:** es el patrón
  estándar de juegos web con audio arbitrario/asíncrono, pero es trabajo innecesario
  aquí — cada `.play()` real ya ocurre dentro de un gesto fresco (ver Pattern 2). Añadirlo
  sería complejidad sin beneficio.
- **Meter el manifiesto de huellas bajo `public/`:** no tiene ningún consumidor en el
  cliente (solo lo leen el script de generación y el test de CI); publicarlo ahí lo
  expondría innecesariamente y podría confundir al futuro crawler de precacheo de la
  Fase 4 si empieza a listar `public/audio/**` a ciegas.
- **Normalizar/recortar la cadena `speech` antes de hashear:** las 37 cadenas ya pasan el
  gate DC-1 (sin `⚠×›`, ≤120 caracteres, no vacías); hashear el string exacto sin
  `trim()` ni lower-casing mantiene el gate de deriva tan estricto como el de contenido —
  cualquier cambio, por mínimo que sea, debe marcar el audio como desactualizado.
- **Llamar a `afconvert` desde el test de CI:** CI corre en `ubuntu-latest`
  ([VERIFIED: `.github/workflows/*.yml`]) — `afconvert` no existe ahí. El test de deriva
  solo compara huellas y nombra el comando a ejecutar (D-05); nunca invoca al conversor.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Contenedor de audio a partir de PCM crudo | Un parser/writer de WAV genérico con soporte de todos los chunks | Un helper de ~20 líneas que escribe la cabecera canónica de 44 bytes fija (ver §Code Examples) | El caso es fijo: mono, 16-bit, 24kHz, sin metadatos extra — un writer genérico sería sobre-ingeniería para un dato que nunca cambia de forma |
| Reintentos/backoff contra la API de Gemini | Una librería de colas/rate-limiting genérica | Un bucle secuencial con `sleep` fijo entre llamadas + reintento simple con backoff exponencial acotado (2-3 intentos) en el propio script | El volumen (37 llamadas, ejecutadas una vez por el desarrollador) no justifica una dependencia; un límite de tier gratuito de ~3 RPM/15 RPD ([MEDIUM confidence, ver §Common Pitfalls] ya impone el ritmo real) |
| Desbloqueo de audio en iOS | Un helper "AudioUnlocker" con pool de elementos y buffer silencioso | Nada — ver Pattern 2, el gesto síncrono ya cubierto por el código existente basta | Añadir esa capa sería resolver un problema que el diseño actual ya no tiene |

**Key insight:** todo lo que este dominio necesita hand-rollear (WAV header, hash de
huella) es deliberadamente pequeño y fijo; todo lo que parecía necesitar una librería
(desbloqueo de audio, precacheo) resulta innecesario o prematuro dado el diseño existente
y el orden de fases del roadmap.

## Common Pitfalls

### Pitfall 1: Un `await` colado entre el toque y `.play()` rompe iOS en silencio

**What goes wrong:** Si `resolveAudioId`/la lectura del mapa de precarga, o cualquier
lógica intermedia, se vuelve `async` (p. ej. "vamos a comprobar primero si el audio
sigue siendo válido"), el navegador deja de considerar la llamada a `.play()` como
disparada por el gesto del usuario.
**Why it happens:** WebKit ata la autorización de reproducción al mismo tick de evento,
no a "hubo un toque hace poco".
**How to avoid:** Mantener el mapa de precarga como una lectura síncrona (`Map.get`, no
una promesa) y decidir audio-vs-fallback de forma totalmente síncrona dentro de
`announce()`, exactamente como ya exige CLAUDE.md para `speak()`.
**Warning signs:** El audio funciona en desarrollo local (Chrome desktop, políticas más
laxas) pero se silencia sin error visible en un iPad — la señal clásica de esta trampa.

### Pitfall 2: Cuota de la API gratuita de Gemini no alcanza para 37 llamadas seguidas

**What goes wrong:** El tier gratuito de `gemini-2.5-flash-preview-tts` está documentado
en foros de terceros como ~3 solicitudes/minuto y ~15 solicitudes/día [MEDIUM confidence
— cifra de WebSearch, no confirmada en `ai.google.dev/gemini-api/docs/rate-limits`, que
remite explícitamente a la consola de AI Studio por ser específico de cada proyecto].
Con 37 frases + 2-3 variantes de estilo de la prueba D-02, un tier gratuito podría no
completar el lote en un solo día.
**Why it happens:** Los límites de los modelos `-preview-tts` son más estrictos que los
modelos de texto normales de Gemini.
**How to avoid:** Antes de ejecutar el lote completo, comprobar el tier real del proyecto
en `https://aistudio.google.com/rate-limit`; diseñar el script para ser reanudable sin
esfuerzo extra (ya lo es, gracias a D-10: una ejecución que se corta a mitad de camino
por cuota simplemente deja ids sin regenerar, y una ejecución posterior los recoge por
diferencia de huella).
**Warning signs:** Respuestas HTTP 429 de la API a mitad de lote.

### Pitfall 3: El manifiesto de huellas y el fichero de audio se desincronizan si se edita a mano

**What goes wrong:** Si alguien toca `public/audio/*.m4a` o `scripts/voice/manifest.json`
directamente (sin pasar por el script), el gate de CI puede quedar en un estado
inconsistente que no refleja ninguna ejecución real del generador.
**Why it happens:** El manifiesto es la única fuente de verdad de "qué huella generó este
audio" — si se edita fuera del script, dos ficheros que deberían ir siempre juntos se
desincronizan.
**How to avoid:** El script de generación es el único escritor de ambos ficheros; el test
de CI es solo lector. Documentar esto en un comentario en la cabecera de
`manifest.json`-adjacent (o en el propio script).
**Warning signs:** El gate falla nombrando un id que "no debería haber cambiado".

### Pitfall 4: Confundir la fase de escritura con la fase de reproducción para las 2 rutas de dificultad

**What goes wrong:** Generar solo un audio por paso variante (ignorando que
`resolveText`/`resolveAudioId` pueden pedir `normal` o `expert` según la sesión) deja a
la mitad de las partidas (todas las que elijan la otra dificultad) sin audio para esos 2
pasos — cayendo siempre al fallback silencioso, sin que nadie lo note como bug porque
D-07 lo enmascara perfectamente.
**Why it happens:** Es fácil generar solo el `speech` "base" del paso y olvidar que el
campo real que se muestra en pantalla ya viene sobrescrito por la variante.
**How to avoid:** El script debe iterar explícitamente los 4 pares (id, variante) además
de los 33 base — el recuento de `03.1-FINDINGS.md`/este research (33+4=37) es el
contrato a cumplir; un test que cuente "exactamente 37 entradas en manifest.json" (ver
§Validation Architecture) atrapa un olvido de este tipo antes de que llegue a la mesa.
**Warning signs:** El gate de deriva pasa (las huellas cuadran) pero el audio real
escuchado en dificultad Experto suena igual que en Normal para esos 2 pasos.

## Code Examples

### Cabecera WAV canónica sobre PCM crudo (mono, 16-bit, 24kHz)

La API de Gemini TTS devuelve PCM crudo sin contenedor
(`mimeType: audio/L16;codec=pcm;rate=24000`, [VERIFIED empíricamente en
`03.1-FINDINGS.md`]). `afconvert` necesita un `.wav` de entrada válido, así que hay que
anteponer esta cabecera fija de 44 bytes antes de invocarlo:

```typescript
// Source: formato RIFF/WAVE estándar (especificación pública, sin cambios desde los
// años 90) — HIGH confidence, formato fijo y ampliamente documentado.
function wrapPcmAsWav(pcm: Buffer, sampleRate = 24000, bitsPerSample = 16, channels = 1): Buffer {
  const blockAlign = channels * (bitsPerSample / 8)
  const byteRate = sampleRate * blockAlign
  const header = Buffer.alloc(44)

  header.write('RIFF', 0)                                  // ChunkID
  header.writeUInt32LE(36 + pcm.length, 4)                  // ChunkSize = 36 + Subchunk2Size
  header.write('WAVE', 8)                                   // Format
  header.write('fmt ', 12)                                  // Subchunk1ID
  header.writeUInt32LE(16, 16)                               // Subchunk1Size (PCM = 16)
  header.writeUInt16LE(1, 20)                                // AudioFormat (1 = PCM lineal)
  header.writeUInt16LE(channels, 22)                         // NumChannels
  header.writeUInt32LE(sampleRate, 24)                       // SampleRate
  header.writeUInt32LE(byteRate, 28)                         // ByteRate
  header.writeUInt16LE(blockAlign, 32)                       // BlockAlign
  header.writeUInt16LE(bitsPerSample, 34)                    // BitsPerSample
  header.write('data', 36)                                   // Subchunk2ID
  header.writeUInt32LE(pcm.length, 40)                       // Subchunk2Size

  return Buffer.concat([header, pcm])
}
```

```typescript
function fingerprint(speech: string): string {
  return createHash('sha256').update(speech, 'utf-8').digest('hex').slice(0, 16)
```

```typescript
// engine/__tests__/voice-drift.test.ts — sigue el mismo estilo que
// engine/__tests__/content.test.ts: lee el JSON crudo con readFileSync,
// sin pasar por ningún runtime de navegador.
import { readFileSync } from 'node:fs'
import { fileURLToPath } from 'node:url'
import { describe, expect, it } from 'vitest'
import { validateGameDefinition } from '../schema'
import { fingerprint } from '../../scripts/voice/fingerprint'

const contentPath = fileURLToPath(new URL('../../content/marvel-champions.json', import.meta.url))
const manifestPath = fileURLToPath(new URL('../../scripts/voice/manifest.json', import.meta.url))
const game = validateGameDefinition(JSON.parse(readFileSync(contentPath, 'utf-8')))
const manifest = JSON.parse(readFileSync(manifestPath, 'utf-8')) as Record<string, { hash: string }>

describe('deriva contenido ↔ audio (D-04)', () => {
  it('cada frase speech tiene un audio con huella al día; falla nombrando ids y el comando de regeneración', () => {
    const expected = collectSpeechEntries(game) // { id, speech }[] — 33 base + 4 variantes
    const stale = expected.filter(({ id, speech }) => manifest[id]?.hash !== fingerprint(speech))

    if (stale.length > 0) {
      const ids = stale.map(s => s.id).join(' ')
      throw new Error(
        `Audio desactualizado para: ${stale.map(s => s.id).join(', ')}\n`
        + `Ejecuta: npm run voice:generate -- ${ids}`,
      )
    }
  })

  it('el manifiesto tiene exactamente 37 entradas (33 base + 4 variantes de dificultad)', () => {
    expect(Object.keys(manifest)).toHaveLength(37)
  })
})
```
