# Phase 1 — UI Design Contract

> Visual and interaction contract for the game selector, mini-setup, resume prompt, setup step-runner, jump index, and "mesa lista" screens. Generated by gsd-ui-researcher, verified by gsd-ui-checker. Formalizes the three mockups the user approved in `01-CONTEXT.md` (step screen, index overlay, Phase 2 header variant) — those are treated as locked specification, not redesigned here.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none — no shadcn / no component library |
| Preset | not applicable |
| Component library | none — hand-rolled Tailwind v4 components |
| Icon library | none — hand-rolled inline SVG for the 5 fixed icons the app needs |
| Font | Inter (self-hosted woff2), fallback `system-ui, -apple-system, sans-serif` |

**Why no component library (open question #7 resolved):** `STACK.md` deliberately deferred this choice; it does not need revisiting later. This phase is 6 screens, one theme (dark only, no light mode), and almost entirely bespoke tablet chrome (a centered dominant sentence, a 3-band step layout, a full-screen grouped index, a segmented player-count/difficulty picker) that doesn't map onto typical component-library primitives (data tables, forms, dropdown menus). shadcn is a React-only project; the Vue-ecosystem equivalent (`shadcn-vue`) is a smaller, unofficial fork that `STACK.md` did not select. Nuxt UI was explicitly flagged in `STACK.md` as "reasonable to add later... not needed for v1's minimal surface" — that condition still holds. Pulling in a general-purpose library now would import primitives (dialogs, popovers, form validation) this phase doesn't need, for a surface area small enough to hand-build in Tailwind directly. Revisit only if a later phase's screen count or form complexity grows materially (e.g. CONF-01 hero/scenario selection in v2).

**Why no icon library:** the whole app needs exactly 5 glyphs: `≡` (index), `✕` (close), `✓` (done), `●` (current), `‹ ›` (chevrons), `⚠` (warning). Hand-rolled inline SVG (or in some cases plain Unicode glyphs styled with the type system below) avoids a dependency for a fixed, tiny icon set — consistent with the project's "no backend, minimal deps" posture. If Phase 3 adds a mute/speaker icon, add it the same way.

**Why self-hosted Inter, not a CDN font:** the app must work fully offline (OFF-02); a Google Fonts `<link>` would require the service worker to separately cache a third-party origin. Bundling `Inter` as a woff2 in the repo makes it part of the same precached app shell as everything else, with zero extra offline-caching logic. Inter was chosen for wide, well-hinted Latin/Spanish-diacritic coverage (á é í ó ú ñ ¿ ¡) at large display sizes and tabular figures for the step counter (`8 de 21`).

## Spacing Scale

Declared values (must be multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-label gaps, tight inline padding |
| sm | 8px | Compact spacing (e.g. warning icon to warning text) |
| md | 16px | Default element spacing, index row internal padding |
| lg | 24px | Section padding, gap between action sentence and warning line |
| xl | 32px | Layout gaps, side padding of the content band on narrower emulated widths |
| 2xl | 48px | Major section breaks, side padding of the content band at typical tablet width |
| 3xl | 64px | Page-level spacing, outer padding of full-screen overlays |

Exceptions:
- **Tap targets (UI-02): 44×44pt minimum, 48×48dp preferred.** Not a multiple of 4/8, but this is the standard Apple HIG / Material minimum and is treated as a hard floor, not a spacing-scale value. Every tappable element in this phase (`≡`, `✕`, index rows, Atrás, Siguiente, mini-setup segmented options, mesa-lista CTA) must clear this floor regardless of how its surrounding padding is expressed in the 4px scale.
- **Siguiente / Atrás band height: 96px** (unusually generous vs. a typical 44px control). This is deliberate: these are the single most-repeated taps in the whole app, tapped by players whose hands are on cards, from a slight angle, without lifting the tablet. Oversizing well past the HIG floor reduces mis-taps; it is still a clean multiple of 4 (96 = 24×4).

## Typography

Exactly 4 sizes, exactly 2 weights, as required.

| Role | Size | Weight | Line Height | Used for |
|------|------|--------|-------------|----------|
| Display | 2.5rem / 40px | 700 (bold) | 1.2 | The step's dominant action sentence (hero text) — the single largest, most important thing on any step screen |
| Heading | 1.75rem / 28px | 700 (bold) | 1.25 | Screen/overlay titles: "¿A qué juego vas a jugar?", index overlay title, "✓ Mesa lista", block headers minus size (see Label for block headers) |
| Body | 1.25rem / 20px | 400 (regular) | 1.5 | Warning line text, index row step text, mesa-lista checklist items, resume-prompt body copy |
| Label | 1.125rem / 18px | 700 (bold) | 1.2 | Header bar text (both sides), Siguiente/Atrás button labels, index block-group headers (uppercase, secondary-text color), segmented-control option labels |

**Weight usage rule:** 700 always signals "the thing to read/act on first" (hero sentence, buttons, headings, current position). 400 always signals supporting information (warning body, list rows, secondary copy). Never invent a third weight for emphasis — use the accent/warning color instead.

### Why Body and Label sit only 2px apart (deliberate, not a violation)

Body (20px/400) and Label (18px/700) are the closest two tokens in the scale — only 2px (~11%) apart. This is intentional, not an oversight: the two tokens are differentiated primarily by **weight**, not size. Label is compact, high-density chrome text that must sit inside fixed-height bands (the 64px header, the 96px nav band) without crowding — including the Siguiente/Atrás button labels, the app's single most-repeated tap target — so it stays bold (700) and slightly smaller to read as an unmistakable label rather than a sentence. Body is glanced-at supporting prose (the warning line, index rows, checklist items) that needs the more relaxed regular weight and a touch more size for comfortable reading, but has no reason to approach Heading (28px) territory. With the type scale capped at exactly 4 sizes (per the design contract), the remaining headroom between Heading (28) and a legible button-label floor is naturally narrow — the weight contrast (400 vs 700) is what keeps the two tokens visually distinct at a glance, not the size gap.

### Action-sentence character budget (content authoring contract)

The Display-size hero sentence never shrinks-to-fit and never scrolls. At 40px/700 in a ~900–960px content column (see Layout below), a line holds roughly 30–35 characters, so:

- **Hard budget: ≤90 characters** (including spaces and punctuation) per step's action sentence. This wraps to at most 3 lines and keeps the sentence readable as a single glanced-at block.
- If a step's true content needs more than 90 characters, **it must be split into two steps**, not shrunk or truncated. This is not a UI fallback — it's a direct enforcement mechanism for CONT-11 ("un paso = una acción física inequívoca") and D-01's fine-granularity decision: a sentence too long to fit is itself a signal the step is doing more than one job.
- The warning line has a tighter budget: **≤60 characters**, ideally one line, hard-wraps to 2 max.
- The planner/executor must add a content-lint check (can be a simple Zod `.max(90)` / `.max(60)` refinement in the schema, or a Vitest content test) enforcing these — do not rely on manual review alone.

### Objective legibility reasoning (UI-01, D-19)

UI-01 requires legibility "a un brazo de distancia," which CONTEXT.md's D-19 explicitly flags as **not verifiable in Chrome device emulation** — emulation reproduces CSS pixel density, not physical viewing distance. This spec therefore uses defensible, stated reasoning instead of an emulator screenshot as proof:

- The CSS reference pixel itself is defined around a ~71cm (28in) viewing distance at 96dpi — already in the neighborhood of "arm's length." Standard web body-text sizing (16px) is calibrated for *sustained, close, single-reader* reading at that distance.
- This app's hero text is read differently: **glanced at, briefly, potentially by more than one player around the table, some of whom are farther than 71cm** (tablet propped beside the table, not held). That calls for sizing meaningfully above the sustained-reading baseline, not equal to it.
- Display (40px) is roughly 2.5× the 16px baseline — enough headroom to stay legible for the player seated farthest from the tablet in a typical 4-person session, without requiring anyone to lean in.
- **This reasoning is engineering judgment, not a substitute for real verification.** Per D-19/D-18, the actual gate is the first tabletop playtest on a real tablet at the end of this phase — record there whether 40px genuinely reads at the far side of the table, and adjust the Display token (not the philosophy) if it doesn't.

## Color

All values computed against WCAG 2.1 relative-luminance contrast ratios (formulas applied by hand, not a tool — reproducible from the hex values below).

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) — background | `#14161C` | App background behind everything; the content band of every screen |
| Secondary (30%) — surface | `#1E212B` | Header band, nav/button band, index overlay panel, mesa-lista checklist rows, mini-setup card |
| Primary text | `#F2F3F5` | Hero action sentence, headings, primary button label surfaces |
| Secondary text | `#9AA0AC` | Header session-context text, index block-group labels, unvisited index rows, resume-prompt supporting copy |
| Accent (10%) | `#2F81F7` (blue) | **Reserved for exactly:** the Siguiente button fill, the index overlay's `●` current-step mark, the `✓` done-marks in the index overlay and in the mesa-lista checklist, the mini-setup's selected segmented option |
| Warning | `#FFB020` (amber) | **Reserved for exactly:** the `⚠` icon + warning-line text on steps that have a trap (D-05) — never used for anything else, so its appearance always means "this step has a trap" |
| Destructive | `#FF5C5C` (red) | **Reserved for exactly:** the "Empezar nueva" confirm action in the resume-vs-new prompt (SETUP-04/05, the one destructive action in this phase) |

**Why not pure black/white:** the app is used in a dim room (UI-05) at a locked screen brightness for potentially hours. Pure `#000` against pure `#fff` text maximizes glare/halation on OLED tablet panels and produces eye strain over a long session; `#14161C` (near-black, slight blue-charcoal) and `#F2F3F5` (near-white, not `#fff`) keep contrast very high while softening that edge.

**Verified contrast ratios (relative luminance, WCAG formula):**

| Pair | Ratio | Passes |
|------|-------|--------|
| Primary text `#F2F3F5` on background `#14161C` | 16.3:1 | AAA (needs 7:1) |
| Secondary text `#9AA0AC` on background `#14161C` | 6.9:1 | AA (needs 4.5:1), near-AAA |
| Primary text `#F2F3F5` on surface `#1E212B` | 14.5:1 | AAA |
| Warning `#FFB020` text on background `#14161C` | 9.9:1 | AAA |
| Destructive `#FF5C5C` text/icon on background `#14161C` | 6.0:1 | AA |
| Dark navy `#0B1220` label on Accent `#2F81F7` button fill | 5.00:1 | AA (normal text, needs 4.5:1) |
| Dark navy `#0B1220` label on Destructive `#FF5C5C` fill | 6.19:1 | AA (normal text, needs 4.5:1) |
| Accent `#2F81F7` glyph (`●` current-mark / `✓` done-mark) on background `#14161C` | 4.83:1 | Passes WCAG SC 1.4.11 Non-text Contrast (needs 3:1 for graphical objects) |
| Accent `#2F81F7` glyph (`●` current-mark / `✓` done-mark) on surface `#1E212B` | 4.29:1 | Passes WCAG SC 1.4.11 Non-text Contrast (needs 3:1 for graphical objects) |

**Text-size conformance note (button labels):** the two button-label rows use the Label token (18px/700). WCAG's large-text 3:1 bar only applies at ≥18.66px bold (or ≥24px regular) — Label sits just under that bold cutoff, so the stricter **4.5:1 normal-text bar** governs both, not the 3:1 large-text bar. Both pairings clear 4.5:1 regardless (5.00:1 and 6.19:1), so the AA verdict stands unchanged — only the cited bar in an earlier draft of this table was wrong, not the pass/fail outcome.

**Non-text contrast note (accent-as-glyph rows):** the last two rows cover the accent color used as a bare graphical mark (the index overlay's `●` and `✓`), not as text. The governing rule there is **WCAG SC 1.4.11 Non-text Contrast** (3:1 floor for graphical objects and UI component states), not the 4.5:1 text-contrast rule used above — both pairings clear it comfortably.

**Button label color rule:** any solid-fill button (Siguiente, the resume prompt's "Empezar nueva" / "Continuar") uses `#0B1220` (dark navy) label text on its accent/destructive fill, not white — computed above as the higher-contrast pairing for a saturated fill.

│              fuera de la partida                      │    background color. Content is a
│                                                        │    vertically CENTERED block (not

│                                                        │    constrained to a ~900-960px
│                                                        │    column with 48px side padding
├──────────────────────────────────────────────────────┤
│   ‹ Atrás              │        SIGUIENTE  ›          │  ← Nav band: 96px fixed height,
└──────────────────────────────────────────────────────┘    surface color. Atrás ~35% width,

- **Header band (64px fixed):** three zones — left (section + position), right (session context), far-right (`≡`, 48×48dp tap target). This exact three-zone contract is what must survive into Phase 2's `RONDA 4 · Villano · 3 de 6` variant unchanged (D-11) — only the left zone's *content* changes, never the band's structure or height.
- **Content band (flexible, vertically centered):** the action sentence + warning line render as one centered block, not top-aligned — because step count varies (some steps have a warning line, most don't) and top-alignment would make the vertical position of the sentence jump around between steps, which is disorienting when glancing quickly. Gap between action sentence and warning line: 24px (`lg`).
- **Nav band (96px fixed):** Atrás is visually secondary (surface-colored, primary-text label, no fill) and narrower; Siguiente is the accent-filled, wider, unmistakably primary control — both within thumb reach without lifting the tablet (UI-03), both ≥48px tall well past the 44pt floor.

## Orientation & Rotation Behavior (UI-04)

UI-04 requires: "La interfaz se presenta en horizontal y no se reorganiza al rotar el dispositivo." This is a web app running in a normal (or, later, installed) browser tab, not a native app, so the enforcement mechanism has to be honest about what a browser tab can actually guarantee.

**Why this can't be a hard OS-level lock in Phase 1:** the Screen Orientation API's `screen.orientation.lock('landscape')` is the only way to truly *prevent* the OS from rotating the viewport, but per spec it only works reliably inside a **fullscreen** context and/or an **installed PWA** on most mobile browsers — a plain tab silently ignores or rejects the call. PWA installability (manifest, service worker, install prompt) is explicitly Phase 4 scope (`01-CONTEXT.md`'s phase-boundary note: "La instalación PWA... se prepara aquí pero se ejecuta conjuntamente cuando el usuario tenga las cuentas creadas" refers to deploy; install itself is Phase 4 per `FEATURES.md`/`REQUIREMENTS.md` phase mapping). Phase 1 cannot depend on a mechanism that only works post-install. Calling `screen.orientation.lock()` here would silently no-op on most devices and give a false sense of enforcement.

**Decision: a portrait-blocking overlay, not a letterboxed/scaled landscape layout.** When the viewport is in portrait, the app shell is fully hidden and replaced by a full-screen blocking overlay instructing the user to rotate back — nothing reflows, nothing partially resizes. Rejected alternative: keeping the landscape layout rendered at a fixed aspect ratio and letterboxing/scaling it to fit inside a portrait viewport. Rejected because (a) it requires nontrivial CSS transform/scale math to keep touch targets at real tap size inside a shrunk, letterboxed canvas — directly risking the UI-02 44/48pt tap floor; (b) it's harder to verify correctly under Chrome device-emulation rotation, which is this phase's only available test method (D-18); (c) the tablet is already assumed **propped beside the table**, not held (D-18) — portrait is an accidental/rare state to recover from, not a state worth preserving a usable reading experience in. A blocking overlay makes "no se reorganiza" literally true (the app shell simply is not rendered while in portrait) with the least implementation risk.

**Overlay content and copy (Spanish, vosotros voice — consistent with the rest of the app):**

```
┌────────────────────────────┐
│                              │
│                              │
│        Girad la tablet       │  ← Heading 28/700, primary text,
│                              │     centered
│  Esta aplicación se usa      │  ← Body 20/400, secondary text,
│  en horizontal.              │     centered, max ~400px column
│                              │
│                              │
└────────────────────────────┘
```

- Background: `#14161C` (Dominant) — same as the rest of the app, no new surface color introduced.
- No new icon: deliberately text-only, consistent with the "exactly 5 fixed glyphs" icon rationale above — a rotate glyph would be a 6th one-off icon for a state that (per D-18) should rarely occur once the tablet is propped in place.
- The overlay has no dismiss control and no interaction — it clears itself automatically the instant the device is back in landscape (pure CSS, no JS timer/listener needed for the visual state).

**Viewport meta (executor must add to the document `<head>`):**

```html
<meta name="viewport" content="width=device-width, initial-scale=1, maximum-scale=1, user-scalable=no" />
```

`maximum-scale=1, user-scalable=no` prevents accidental pinch-zoom from a mis-tap during play (this app is not a document meant to be zoomed); it does **not** and cannot enforce orientation — no viewport meta value controls orientation in current browsers. Orientation is handled entirely by the CSS below, not the meta tag.

**CSS / Tailwind contract (orientation media query):**

```css
/* App shell: hidden in portrait, shown in landscape */
@media (orientation: portrait) {
  #app-root { display: none; }
  #orientation-guard { display: flex; }
}
@media (orientation: landscape) {
  #orientation-guard { display: none; }
}
```

Equivalent Tailwind v4 utility classes (this project's actual styling approach): `#app-root` gets `portrait:hidden`, `#orientation-guard` gets `hidden portrait:flex`. Both elements are always mounted in the DOM; only their visibility toggles with orientation, so there is no layout thrash or remount cost on rotation, and the guard is trivially testable via Chrome's device-emulation rotate control (D-18).

**Forward-compatibility (Phase 4, not built here):** once the app is installable as a PWA, its manifest can declare `"orientation": "landscape"`, which most mobile browsers honor for the *installed, standalone* launch context without needing `screen.orientation.lock()` or fullscreen at all. That gives Phase 4 a real, OS-respected lock for users who install the app — Phase 1's CSS-overlay guard remains as the fallback for anyone still running it as a plain browser tab.

## Interaction & State Coverage

### Disabled states — deliberately none for Siguiente/Atrás in this phase

Every step in Phase 1's linear flow has a valid destination in both directions:
- Atrás from setup step 1 → returns to the mini-setup screen (a real screen, not a dead end).
- Siguiente from setup step 21 → advances to the "mesa lista" screen (also a real screen).
- Atrás from "mesa lista" → returns to step 21. Siguiente/"EMPEZAR A JUGAR" from "mesa lista" → Phase 2 (out of scope here, but the button is never disabled waiting for it).

So there is **no disabled Atrás-on-first-step or disabled Siguiente-on-last-step case in Phase 1** — stating this explicitly per the open-question list, rather than silently building unused disabled styling. The one real disabled state in this phase is `MiniSetupScreen`'s confirm CTA, inactive (reduced-opacity, non-interactive) until both player count and difficulty are selected — style: 40% opacity, no accent fill, no pointer cursor.

### Pressed / tap feedback

All tappable elements (Siguiente, Atrás, `≡`, index rows, segmented options, cards) get an immediate pressed state on `touchstart`/`mousedown`: 4% darken of the fill (or surface color for outline-style controls) plus a 2% scale-down, released on `touchend`. This exists purely as tactile confirmation for imprecise/angled taps — not a design flourish — given hands are often occupied with cards elsewhere on the table.

### Index overlay open/close

- **Open:** triggered only by tapping `≡`. Transition: 180ms ease-out, fade + 8px upward slide. No backdrop dimming needed — the overlay is full-bleed surface-color content per D-13, it doesn't sit "over" anything.
- **Close:** tapping `✕` only (no outside-tap-to-dismiss, since there is no visible "outside" in a full-screen overlay).
- **Tapping the current step's row (marked `●`):** closes the overlay with no navigation — the user is already there; treat it as equivalent to cancel.
- **Tapping any other row (done `✓` or unmarked upcoming):** closes the overlay AND jumps immediately to that step, no confirmation. Jumps are cheap to undo (Atrás, or reopening the index) so a confirm step would only add friction to the app's second-most-used interaction.
- **Scroll:** the overlay's title bar is pinned; the grouped block list scrolls independently if it exceeds viewport height (relevant once Phase 2's round-loop blocks are added to the same overlay pattern).

### Accidental-touch resistance (open question #8, resolved explicitly)

**Decision: no tap-protection (no long-press, no double-confirm, no cooldown) on Siguiente/Atrás.** Reasoning, stated rather than silently skipped:
- `FEATURES.md`'s accidental-touch risk is drawn from *handheld phone* contexts (players holding the device with card-occupied hands brushing the screen). This app is explicitly **not held** — CONTEXT.md locks the tablet as "propped beside the table" (D-18/PROJECT.md), so the nav band isn't under a hand holding cards; it's a deliberate reach.
- Both Siguiente and Atrás are trivially reversible (an accidental Siguiente is undone by one Atrás tap and vice versa) — the cost of a mis-tap is one extra tap, not lost state or a broken sequence.
- FLOW-01 explicitly requires Siguiente to be "the single most prominent element" — adding a hold-to-confirm gesture to the single most-repeated interaction in the entire app (tapped ~21+ times per setup alone) would directly fight that requirement and add real friction for a real cost only in an unheld/propped device that this phase already assumes.
- The one place friction IS warranted is the destructive "Empezar nueva partida" action (SETUP-04/05, genuine data loss, not reversible) — that gets the explicit `ConfirmDialog`, see Copywriting Contract.

## Forward-Compatibility Notes (labelled, not built here)

- **Header (D-11):** the header's three-zone contract (left: section+position, right: session context, far edge: `≡`) must survive Phase 2's `RONDA 4 · Villano · 3 de 6` swap with only the left zone's *content* changing — the `AppHeader` component's props (`sectionLabel`, `position`) are already generic enough for that; do not name them `setupSection`/`setupPosition`.
- **Mute icon (Phase 3, VOZ-02):** reserve a 44×44dp icon slot between `sessionContext` and `≡` in the header's right zone. Not built in this phase, but the header's flex layout should not assume exactly two children on the right.
- **Wake lock battery notice (Phase 3, UI-07):** no UI surface needed in this phase; note only so the mini-setup or mesa-lista screen isn't accidentally treated as the final screen before gameplay in a way that would make a later notice awkward to insert.
- **PWA install prompt / offline indicator / update banner (Phase 4):** no UI surface needed in this phase; the header and nav bands should not be assumed to be the only persistent chrome — a future top-of-screen banner (update available) must be able to appear without pushing the 64px header band's own layout math. Also see **Orientation & Rotation Behavior (UI-04)** above — Phase 4's manifest can add a real `orientation: landscape` lock once install exists, on top of (not instead of) the CSS overlay guard built in this phase.
